# Brief 135: the Likha encoder gets safer rules and learns from past corrections

## Why
A backtest of 1,487 real orders (2026-10-22) compared Likha's encode (exact copy of the sheet scripts) with the final orders and with the sheet's own output, both followed by the existing Validate rules (`MacroChecker::validateRow`). After Validate the sheet let 0 wrong addresses through; Likha let 7 through (2 clearly wrong). Causes, all inherited from the scripts, read from Likha's step logs:
- A **GPT fix replaced a correct barangay** that the customer wrote in "Brgy:": "#20 miller st. Brgy. Bungad Q.city Project 7" → Bungad (correct, from the J&T match) was replaced by Project 7; "C Lawis Ext … San Isidro Antipolo" → San Isidro (POB.) replaced by Calawis. The fix runs whenever the encode leaves any remark (e.g. "Province", "MULTIPLE SUGGESTED ADDRESS"), and the checkers then accept it because the word appears somewhere in the chat.
- **"Province only → ✅"** accepted a wrong province the customer had written differently ("Tanqu, San Fernando, La Union" → Pampanga).
- **First candidate** depends on list order ("Pasolod … Cebu City" → CEBULAN via the "cebu" substring).
- **Labels** written as "BARANGAY POBLACION 4" are not J&T labels (staff had to fix them); combinations not in the J&T list (Burauen/Bayog, Laguna Santa Cruz/Inalmasinan) were PROCEEDed.
- **Duplicate orders** of the same customer the same day were PROCEEDed.
The owner also wants the encoder to **learn**: every correction staff or Astra made becomes a note it can look up next time, reviewable and editable, used only when approved.

## Decisions (do not reopen unless something is actually broken)
| Decision | Why |
|---|---|
| **Rule switch** `app_settings.order_encode_rules` = `improved` (default) / `sheet` (exact spec-130 behaviour). Every rule below applies only when `improved`; the step log records which rule fired. | Compare both, roll back without code. |
| **R1 Written barangay wins.** Before any GPT barangay/city fix: if the customer's written "Brgy:" value (from the extracted details; normalised: lowercase, ñ→n, "brgy/barangay/bgy/pob/poblacion" folded, digits and roman numerals equal — reuse the normalisers MacroChecker already has for J&T matching if they fit, read-only) equals a barangay of the current city in the J&T list (whole value, not substring), keep it and skip the barangay fix; same for a written "City:" vs the province's city list. | Bungad, San Isidro. |
| **R2 Province contradiction.** If the customer wrote a province that resolves to a J&T province different from the result, the order is held (reason "Province differs from what the customer wrote"), and "Province only → ✅" does not apply. A written province that resolves to nothing (e.g. "[Please confirm]", "N/A") does not count. | Tanqui/La Union. |
| **R3 Better first candidate.** Among the J&T candidates of the word-by-word match, prefer one whose barangay equals the written "Brgy:" (as R1), then one whose city equals the written "City:", then list order. | Cebulan/Pasil. |
| **R4 J&T labels and guard.** Output province/city/barangay exactly as the J&T list writes them (no "BARANGAY …" prefix rewrite on output; keep it for matching only). PROCEED only if the exact combination exists in `jnt_address.txt`; otherwise hold with the reason. | Labels and invalid combos. |
| **R5 Duplicates.** Hold (reason "Possible duplicate: <order ids>") when the same phone, or the same name + barangay + city, already has an order on the same `ts_date` (in `macro_output` or in today's `order_encodes`), unless the phone is in the Validate whitelist. | Same-day duplicates. |
| **Learning notes — one new table `address_notes`** (additive migration): `written_key` (indexed; normalised written "brgy\|city\|province" from the extracted details, empty parts kept as ""), `written_example` (one raw example, ≤255), `province`, `city`, `barangay` (J&T labels), `source` (`staff_fix` / `astra_fix` / `delivered` / `manual`), `seen` (count), `delivered` (count of those orders delivered by J&T), `conflict` (bool + JSON of the other answers with counts), `status` (`pending` / `approved` / `rejected`), `reviewed_by`, `reviewed_at`, `review_note`, `order_ids` (JSON, ≤20 examples), timestamps. One row per written_key (+ answer). Page \| Key \| Value does not fit (one row per learned address, searched by key, thousands of rows). | The owner: learning that can be looked back at. |
| **Build:** `order-encode:notes-build --days=60` (and daily at 05:30 Manila with `--days=3`) reads `macro_output` orders whose location was corrected (HISTORICAL LOGS with PROVINCE/CITY/BARANGAY entries, or an `ai_checker_logs` row with outcome `fixed`) and orders delivered (`from_jnts.status` = 'Delivered'); for each, the written key comes from the order's extracted details parsed with spec 130's parser (fallback: the encode's parsed parts if an `order_encodes` row exists); the answer is the final PROVINCE/CITY/BARANGAY, only if it exists in the J&T list. Aggregate by key: same answer → seen/delivered up; different answers → `conflict` with counts. New notes start `pending`. A note becomes `approved` automatically only when delivered ≥ 2, no conflict, and source includes a fix (staff/astra); everything else waits for review. Never overwrite a reviewed note's status. | Uses the data we already have (60 days: 6,942 staff fixes, 3,071 Astra fixes, 44,003 delivered). |
| **Use in the encode** (rules `improved`): (1) exact approved note for the written key → set province/city/barangay from it, skip the GPT location fixes, log `NOTE_HIT`; still run the checkers and R4/R5; (2) otherwise pass up to 5 approved notes with the same written city or province (closest by token overlap) to the GPT barangay/city/province fix prompts as "Past corrections (customer wrote → correct J&T address)" examples; (3) otherwise as today. The lookup must be index-only (no full scan per order). | Notes are searched, not read in full. |
| **Review page `/order-encode/notes`** (CEO): search by written text / place, filters (status, source, conflict, delivered ≥ n), per note the examples (links to the orders), the conflict breakdown; actions approve / reject / edit answer (only to a J&T combination) with a note, bulk approve of a filtered selection; counts per status. Also `order-encode:notes-review --approve-where="…" --reviewer="…"` for scripted review with a dry-run flag. English UI. | Everything shown and editable; the analyst can review in bulk. |
| **Backtest command** `order-encode:backtest --source-mode=backtest2 [--limit]`: re-encodes the stored inputs of an earlier test (rows with that mode) under the current rules into a new mode (e.g. `backtest-<timestamp>`), then prints, for Likha and for the sheet's output if `tmp_sheet_out` exists (skip if not): orders, PROCEED, correct (final STATUS = PROCEED and same location, Ñ = N), wrong, pending, blank address — each **after `MacroChecker::validateRow`** (same arguments as the Validate button; phone as 10 digits). Real GPT calls only when run on the server. | One command to prove the change on the same 1,487 orders. |
| `/order-encode/final` shows NOTE_HIT and which R-rule held an order. | Visible. |

## Threat model and risk
Untrusted: customer text, GPT output, note examples shown on the page (escape). Trusted: CEO review actions. Risk tier: medium — changes encode decisions (shadow only today; live via the Encode order step later). Notes must never contain phone numbers or names (store only the address parts and order ids).

## Done when
- Tests per rule R1–R5 with the real cases above as fixtures (Bungad/Project 7, San Isidro/Calawis, Tanqu La Union, Pasolod Cebu City, "BARANGAY POBLACION 4", Burauen/Bayog, three same-day duplicates); `sheet` mode reproduces spec 130 results unchanged; notes build (staff fix, Astra fix, delivered, conflict, auto-approve rule, never overwrite reviewed), note hit skips GPT fixes, examples passed to the prompt (≤5), lookup uses the index; review page actions, bulk approve, edit only to a J&T combination, CEO only; backtest command output on a seeded set.
- `php vendor\phpunit\phpunit\phpunit tests/Feature/OrderEncode tests/Feature/Chatblast tests/Feature/PageSettings tests/Feature/Botcake tests/Feature/NightRun` plus your new tests pass; note the known local-only failure (missing Google credentials file) separately.
- Result: files, the migration, settings keys, the normalisation rules used for "written" keys, the auto-approve rule, commands and schedule, commits.

## Out of scope
Changing Validate, Astra, MacroChecker or the imports; deploy; switching any flow to the Encode order step.
