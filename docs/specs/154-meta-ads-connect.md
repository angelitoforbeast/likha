# Brief 154: staff connect their Facebook once; Likha pulls the Ads Manager report from the Meta Marketing API

## Why
Five staff export the Ads Manager report (per ad, per day, last 7 days, XLSX) three times a day (~10:00, 15:00, 18:45) and upload it at /ads_manager/report (`AdsManagerReportController::store` → `ProcessAdsManagerReportsUpload`, upsert into `ads_manager_reports` by `day` + `ad_id`; ~14 files and 13–15k rows a day). The 13 ad accounts (`ad_accounts` table) sit in different Business Managers and the owner does not want them in one BM. So each ad-account owner connects their own Facebook in Likha (an integration on their Likha account; Likha login stays email + password), and Likha reads their ad accounts with their token.

## Facts (Meta docs, checked 2026-10-26; treat "likely" as to be proven in the pilot)
- One Meta app (Development mode, Facebook Login + Marketing API products, not linked to a business). Each staff member is added as a Tester and accepts. Standard Access to `ads_read` works for users with a role on the app (confirmed); whether it covers their ad accounts in other BMs is likely, not confirmed — the pilot will tell.
- Plain Facebook Login (OAuth dialog, `scope=ads_read`), not "Login for Business". Code → short token → `GET /oauth/access_token?grant_type=fb_exchange_token&client_id&client_secret&fb_exchange_token=` → long-lived user token (~60 days; no server-side refresh; expires early on password change/logout; error 190 = reconnect). `GET /debug_token` gives `expires_at` and `data_access_expires_at` (`ads_read` is exempt from the 90-day data-access expiry).
- `GET /me/adaccounts?fields=account_id,name,account_status` lists the accounts the user can read.
- Insights: `GET /act_{id}/insights?level=ad&time_increment=1&date_preset=last_7d` (or time_range) with fields: `ad_id, ad_name, adset_id, adset_name, campaign_id, campaign_name, reach, impressions, inline_link_clicks, spend, actions, cost_per_action_type, results, cost_per_result, attribution_setting, date_start, date_stop`, paginate `paging.next`. "Messaging conversations started" = `actions[action_type=onsite_conversion.messaging_conversation_started_7d]`. Purchases = `actions` purchase/omni_purchase (verify in pilot). `results` is a list with `indicator` + `values[]` (shape to be seen live); Result type has no field: derive from the ad set's `optimization_goal`.
- Non-insight columns: ad set `effective_status, daily_budget, lifetime_budget, start_time, end_time, optimization_goal`; campaign `effective_status`; creative `title, body, object_story_spec, page_welcome_message` (welcome message + quick replies/ice breakers; may need a Page token for partner flows; readability at Limited tier unknown). Page name for `page_name`: the ad's promoted page (`object_story_spec.page_id` → name) — match how the export's "Page name" column is filled today.
- Limited access tier: heavily rate-limited per ad account; read headers `x-business-use-case-usage` / `x-fb-ads-insights-throttle`, back off on codes 4/17/613. Graph version: put it in config (default v25.0).

## Decisions (do not reopen)
| # | Decision | Why |
|---|---|---|
| 1 | **Connect = an integration on the Likha user**, a "Connect Facebook" button on a page the uploaders use (on /ads_manager/report, plus the user's profile if there is one). Callback stores the long-lived token (encrypted), the FB user id/name, expiry, and the list of ad accounts it can read. Disconnect removes them. | Owner: login stays email; Facebook is an added integration. |
| 2 | **Lean schema:** check the owner's row-based precedent first (`page_settings`: page_name/provider/key/value, `is_secret`, active, replaced_at, created_by) and `ad_accounts`. No new table unless rows cannot hold it; if you add one, justify it in the result. | Owner's rule: no new table when rows fit. |
| 3 | **Shadow first:** a command + "Compare with uploads" button that pulls the API data for a date range and compares it with `ads_manager_reports` rows (same `day` + `ad_id`): per ad account, rows only in API / only in upload / differing spend, results, reach, link clicks, messaging conversations, with % differences. Writes nothing to `ads_manager_reports`. | Prove the numbers before replacing the uploads (same as the encode shadow). |
| 4 | **Write mode behind a setting** (off by default): when on, a schedule (default 3×/day at 10:00, 15:00, 18:45 Manila, configurable) and a **"Sync now"** button upsert into `ads_manager_reports` by `day` + `ad_id`, the same columns the upload fills, and log a run like the upload log (`upload_logs` type e.g. `ads_manager_api`, inserted/updated/skipped, who/when). Uploads keep working. | One click; nothing changes until the owner turns it on. |
| 5 | **Token health:** the page lists each connected person, their ad accounts, last sync, expiry; a red "Reconnect" when expired/190 or within 7 days of expiry. | ~60-day tokens. |
| 6 | **Config/secrets:** `META_ADS_APP_ID`, `META_ADS_APP_SECRET`, `META_ADS_GRAPH_VERSION`, redirect URL from `config('app.url')`. Missing app id → the Connect button shows "Meta app not set up yet" (no crash). Tokens never logged or shown. | Secrets stay in .env. |
| 7 | Access: the same roles that can upload the Ads Manager report can connect, compare and sync; turning write mode on is CEO only. Every connect/disconnect/sync/mode change is logged with user and time. | Same as the upload today. |

## Cases (add as S-154 to qa/stories.md)
P1: .1 Connect: OAuth redirect has `scope=ads_read` and a state; callback exchanges for a long-lived token, stores it encrypted with expiry and the ad accounts; bad/missing state → refused; .2 no app id → "Meta app not set up yet"; .3 Compare (faked API with 2 accounts, pagination, an ad in API only, an ad in upload only, a spend difference) → the right report, nothing written; .4 field mapping: each `ads_manager_reports` column filled from the faked API as the upload would (spend→amount_spent_php, inline_link_clicks→link_clicks, messaging conversations from actions, results/cost_per_result, budget/type, delivery, starts/ends, headline/body/welcome message/quick replies when present); .5 Sync now with write mode on upserts by day+ad_id (insert new, update existing), logs the run; with write mode off it refuses; .6 error 190 → token marked expired, "Reconnect" shown, other people still sync; rate-limit codes 4/17/613 → backoff, partial run logged, no crash; .7 the schedule runs only when write mode is on; .8 token never appears in logs, responses or the page; .9 roles: uploader roles can connect/compare/sync, only CEO toggles write mode; .10 Disconnect removes the token rows.
