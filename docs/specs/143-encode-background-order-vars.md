# Brief 143: Encode order runs in the background everywhere; flows read the order's result through order_* variables

## Why
Spec 137's new "Encode order" block (`app/Services/OrderEncode/FlowEncode.php`, FlowEngine `encodeMacro`, `RunEncodeAstra`, the AI-table wait) suspends the flow up to 120 s for the result and fails in a sequence step ("Encode order cannot wait in a sequence step"). Live test 2026-10-25 01:32 on Tech Flask Ph: the sequence step's Upload to macro inserted row 1058227, then Encode order failed, so the row stayed unencoded. The owner: encoding is a background process like the Astra check; it must work in any flow without waiting, and he checks the result later in a sequence (PROCEED → no question; otherwise an AI step decides what to ask).

## Decisions (do not reopen unless something is actually broken)
| Decision | Why (owner) |
|---|---|
| **Encode order never waits.** In any run (main flow, sequence step, anything), it queues the encode of the target row on the express lane (`encode-live`), then Astra on `astra-live` when the encode does not PROCEED (block checkbox, default on; kill switch `order_encode_spot_astra` respected), writes the results into the row exactly as 137 does (address fields, name/phone rule, STATUS only by first-encode rules, staff edits kept, "Likha encode" log lines, final/waybill rows untouched), and the flow continues on **next** immediately. Remove the wait/suspend path, the "Wait up to" setting and the encode_* variables set on resume (old saved configs with `wait` are ignored, not errors). | "no need din ng wait, background process yan, kahit nga hindi yan ilagay sa sequence dapat gagana". |
| **Target row**: the row Upload to macro wrote in this run; if none, the customer's open row (page + PSID, STATUS blank, within 24 h, crossing midnight — the 136/137 rule); if none of those, the block goes to **failed** with a note ("no order row to encode") and nothing is queued. Idempotent: the same row is not queued twice while an encode for it is queued/running. | "encode order lang, pero based dun sa order id, psid, macro output id". |
| **order_* variables** available in every flow (main and sequence), computed when read from the customer's latest macro_output row on this page (page + PSID; the newest row of the last 24 h, else the newest row of the last 7 days): `order_row_id`, `order_status` (PROCEED / CANNOT PROCEED / blank), `order_checker` (APP SCRIPT CHECKER), `order_hold_reason` (one of address, duplicate, name, phone, price, other — derived from the row's hold/remark/AI ANALYZE the same way 137's hold_reason was; blank when PROCEED), `order_province`, `order_city`, `order_barangay`, `order_address`, `order_name`, `order_phone`, `order_encode_state` (none / queued / running / done / failed, from the latest order_encodes row and its Astra job). Usable in Condition (Variable field) and in templates/AI prompts (`{{order_status}}` etc.); listed in the editor's variable picker under an "Order" group with one-line help. No phone or name in logs. | "via sequence ko ichecheck kung nag-proceed or hindi, or kung ano status… if hindi pa, dun mag-aanalyze ai kung ano itatanong". |
| The Encode order block's help text says it runs in the background and that the result is read with order_* variables later (e.g. in a sequence step after a delay). Publish notice: keep "no Upload to macro before it" only as a soft hint (the open-row fallback exists). | Everything shown and editable. |
| Legacy block, Upload to macro, express lane, Test tab behaviour (Test: nothing queued; order_* read normally), shadow pages: unchanged except as above. | Small change. |
