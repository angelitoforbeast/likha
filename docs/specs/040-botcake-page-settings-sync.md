# Brief 040: per-page settings as Page | Key | Value, and Likha finds customers' Botcake PSIDs through the Botcake API

## Why

No Likha order has had a Botcake PSID since early September: the sheet the PSID import reads stopped receiving rows, so delivery messages reach almost nobody. The Botcake public API lists a page's customers (with psid, full_name, phone_number), so Likha can find the PSIDs itself. Each page's Botcake page id and token now live only in a Google Sheet tab ("BOTCAKE API": A Page Name, B API KEY, C BOTCAKE ID, D FLOW ID). The owner wants per-page settings in Likha as rows (Page | Key | Value) so a new kind of setting (another flow, another service's token) is a new row, never a new column, with a page to manage them.

Botcake facts (verified against the live API, 2026-10-16/17): base `https://botcake.io/api/public_api/v1`, header `access-token: <page token>`. `GET /pages/{page_id}/customer?page=N` returns 10 customers per call (no size or search parameter works), as a JSON array of {id, psid, full_name, phone_number (array of strings, often empty), …}; an empty array after the last page. Order observed: newest subscriber first (not guaranteed). `GET /pages/{page_id}/custom_fields?page=N` (50 per call) returns {success, data: [{id, name, type}]}: a cheap call to test a token. A short test saw no 429 up to 5 requests a second; the real limit is unknown.

## Decisions already made (do not reopen)

| Decision | Why |
|---|---|
| One table `page_settings`: page_name (equal to `macro_output.PAGE`, compared trimmed and case-insensitive), provider (e.g. `botcake`), key, value (text), is_secret, active, replaced_at, created_by, created_at. One ACTIVE row per page + provider + key; changing a value marks the old row replaced (kept as history) and adds a new one. No columns per setting, no other settings tables | Owner: "Page \| Key \| Value … para pwede magadd every time"; his rule: no new table unless needed |
| Secret values (tokens) are stored encrypted (Laravel `Crypt`), never returned to any page, API or log; the page shows only the last 4 characters | Tokens |
| Known keys are validated in code: `botcake.page_id` (digits), `botcake.token` (secret, non-empty), `botcake.flow.<purpose>` (digits; purposes like on_delivery, in_transit, broadcast, shipping), `botcake.field.<name>` (digits), `botcake.token_status` (written by the system: ok / invalid + checked time). Any other key is allowed as free text, with a "secret" checkbox | Typos like "442139078/" must not get in; new kinds still need no code |
| UI `/page-settings`, CEO only (404 for others): list grouped by page with filters (page, provider, key), add / edit (a new value replaces) / deactivate, history per row, a "Test token" button (one custom_fields call: ok or invalid) and a "Sync Botcake customers now" button per page showing the last sync's counts. Edits are logged with who and when | Owner: "need ko ng ui" |
| One-time import command `page-settings:import-botcake {spreadsheetId} {--range='BOTCAKE API'!A2:D} {--apply}`: dry run prints per row page name, whether it matches a `macro_output.PAGE` (any date), and which keys it would write (never the token); `--apply` writes `botcake.page_id`, `botcake.token`, `botcake.flow.shipping` (column D, digits only; anything else is reported and skipped) | Move the settings out of the sheet once, on the server |
| Botcake customers go into the existing `botcake_psids` table (spec 039) as a lookup: add columns `source` (sheet / api), `phone_numbers` (json), `subscribed_at`, `last_interactive_at`, `botcake_customer_id`; API rows use status `available` (never expire, never "waiting"); one row per page + psid (update name/phones on change) | Reuse 039's table, no new table |
| Command `botcake:sync-customers {--page=} {--full}`: for each active page with `botcake.page_id` and `botcake.token` (or the one page): incremental = read pages 1, 2, … and stop at the first batch whose 10 psids are all already stored for that page (or an empty batch); `--full` reads to the end. At most 2 requests a second per page, one page at a time; on 429 or 5xx wait and retry with backoff (max 3), then stop that page and report. A 401/403 or `success:false` on the token marks `botcake.token_status` invalid and stops that page. Each run is recorded in `botcake_psid_import_runs` (source api, page, batches read, customers new/updated, seconds, error) | Respect Botcake; the list is newest-first |
| Matching after each page's sync (and in the 039 hourly run for pages with tokens): `macro_output` rows of that PAGE from the last 30 days (ts_date) with empty `botcake_psid`: (1) normalised `fb_name` (trim, collapse spaces, lower case) equal to exactly ONE distinct psid among that page's `available` rows → write it; (2) else the order's phone (`PHONE NUMBER` or `edited_phone_number`, normalised to 09XXXXXXXXX) equal to a phone of exactly ONE customer → write it; (3) two or more candidates → write nothing and count it as ambiguous. Never overwrite a non-empty `botcake_psid`. Counts per run: matched by name, by phone, ambiguous, no match | Wrong waybill/COD to the wrong person is worse than no message |
| The UI shows per page: customers stored, last sync, and the orders of the last 30 days still without a PSID split into ambiguous / no match (live query, names shown only to the CEO there) | So the owner can see and fix |
| Schedules: hourly incremental sync + matching for pages with tokens, weekly `--full` on Sunday 01:00 Manila, `withoutOverlapping`; both run only when `config('services.botcake.sync_enabled')` (env `BOTCAKE_SYNC_ENABLED`, default false) is true. 039's own schedule is unchanged | Released switched off; turned on after a one-page test |

## Do

Part A (commit): `page_settings` migration, model, validation, the UI, the import command. Part B (commit): the `botcake_psids` columns, the HTTP client for Botcake (one small class, timeouts, backoff, never logs the token), the sync command, the matching, the schedule entries behind the flag. Keep 039 working unchanged.

## Tests

Fake HTTP for Botcake. Settings: one active row per key, replace keeps history, token encrypted at rest and never in any response or log, known-key validation rejects "442139078/", free keys accepted, CEO only (404 for others), test-token ok / invalid. Import: dry run writes nothing and never prints a token; `--apply` writes the three keys, skips a bad flow id. Sync: incremental stops at the first all-known batch; full reads to the empty page; 429 then success retries; 401 marks the token invalid; rate stays ≤ 2/s (assert the sleeps through an injectable clock). Matching: unique name → written; two psids with the same name → ambiguous, nothing written; phone match when the name fails; non-empty psid never overwritten; orders older than 30 days untouched. Schedules exist and do nothing when the flag is off. Red first where natural. The whole suite must pass except the known `ExampleTest` (and `ImportStartTest` in a fresh worktree).

## Out of scope

Sending messages; the chatblast sheet and its script; deleting the sheet tab; any change to how orders or exports work beyond writing `botcake_psid`.
