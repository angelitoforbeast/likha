# Brief 136: chatbot orders reach macro_output through the Encode order step, one row per customer per day

## Why
The bot flow's "Encode order" step (spec 132) already creates the macro_output row itself in live mode (`app/Services/OrderEncode/FlowHook.php` node(), `app/Jobs/EncodeOrder.php`, `Runner.php`, `LiveOrder.php`), so orders no longer need the Google Sheet. Before any page uses it live, the owner wants the logic right for repeat customers, and two additions: a held order is fixed by Astra on the spot, and if Astra cannot fix the address, the customer is asked for it through a chatbot sequence. No order has gone through the live path yet (0 live `order_encodes` rows), so nothing existing needs migrating.

Problems found in the code:
- `LiveOrder::create` finds an existing order with `OrderIdentity::find` (TIMESTAMP at minute precision + PAGE + fb_name, no PSID): two orders of one customer in the same minute merge, two people with the same FB name in the same minute merge, and the same customer in different minutes gets separate rows.
- `Runner::duplicates()` (R5) runs before `LiveOrder::create()`, while `order_encodes.macro_output_id` is still null, so a re-encode would hold itself as "Possible duplicate" of its own row.
- `Runner::fail()` writes the sheet fallback unless `macro_output_id` is set, so a failed re-encode of an existing row would append a sheet row.
- The chat text each encode reads (`Encoder::allUserInput`, the flow's input cell) may still carry a previous order's messages.
- `NightAstraRun::selection` takes every blank-STATUS row of the day.

## Decisions (do not reopen unless something is actually broken)
| Decision | Why (owner) |
|---|---|
| **One macro_output row per customer per day; only one order is accepted per customer per day.** A customer = PAGE + PSID (`botcake_psid`). For rows made by the imports (no PSID), match PAGE + fb_name on the same ts_date. Customers are never linked by phone: a second FB account with the same phone gets its own row, and Validate already refuses the duplicate phone. | "per day ngayon, 1 row lang, one order accept per day lang din"; "nadidisregard to, di ia-allow ng validate". |
| **Re-triggers update, never duplicate.** A new run of the step for a customer with an open row (STATUS blank, i.e. not PROCEED and not CANNOT PROCEED) created in the last 24 hours links its new `order_encodes` row to that macro_output row and re-encodes it. This crosses midnight: an order at 23:59 and a reply at 00:01 update the same row, which keeps its original TIMESTAMP and ts_date. The order's day comes from the order time (cell A, Manila), never the job time or UTC. | "medyo tama nga yan" (on the 23:59 / 00:01 case). |
| **A row that is final is never changed.** If the customer's row today is PROCEED (or has a courier status / waybill), a later order or message is not accepted: the row is untouched in every column, the encode is stored with a visible note "second order not accepted: row <id>" (on /order-encode and as a chat event), with no Astra, no sequence and no sheet write. A CANNOT PROCEED row does not block: a new order that day makes a new row. | One order per day; a CANNOT order is rare and must not be lost. |
| **What an update may change:** ADDRESS, PROVINCE, CITY, BARANGAY, ITEM_NAME, COD, all_user_input / extracted details, AI ANALYZE, APP SCRIPT CHECKER and STATUS (to PROCEED only through the same rules as a first encode), only while STATUS is blank, and never a field staff already edited (`edited_*` flag set or a person's entry in HISTORICAL LOGS). Never TIMESTAMP, ts_date, PAGE, fb_name, botcake_psid. Each update adds one HISTORICAL LOGS line per changed field in the existing format with the user "Likha encode" (not a person); reports that count staff activity from the logs must not count these lines. | Staff work is never overwritten; the logs show what the automation did. |
| **The right conversation.** Each encode reads only this order's messages; on a reply to the address question it reads the original order text plus the reply. Old `all_user_input` from an earlier order is never appended into a new order. If the flow's input cell cannot be trusted to hold one order only, store per run what was read and build the text from the runs linked to this row. | The second order must not pick up the first order's address. |
| **R5 duplicates** stays for different customers only (different PSID, same name + barangay + city, or same phone as today), runs after the link to the day's row is made, and never counts the customer's own linked row (also across midnight). Amend S-135.15/.16 and the "different run is a new order" wording of S-132.9 / S-130.16 accordingly and list the changes under "Story changes". | Decision 1 removes same-customer duplicates. |
| **Astra on the spot.** When a live encode ends without PROCEED, queue one Astra run for that row at once (reuse the single-row path the night run uses, `RunNightAstraRow` / `AstraEncoder` and its `ai_checker_logs` writing; do not change Astra's prompt or rules). A per-row lock prevents two Astra runs (on-the-spot, re-trigger, night run) writing the same row together. App setting `order_encode_spot_astra` (on/off, default on, CEO only) is the kill switch. Astra errors or a missing key leave the row held and the next step still runs; the order is never lost. | "same na din naman e, on the spot lang pinaprocess yung order". |
| **The night run may still run Astra again** on rows Astra tried on the spot and could not fix (accepted double cost for now). Do not add a skip. | "kahit ulitin muna" (a follow-up will revisit it). |
| **Address question.** If Astra (or the encode, when the kill switch is off) leaves the row held **because of the address** (province, city, barangay or address line unresolved, R2, R4, the address checker not ✅), subscribe the customer once (`ChatbotSequences::subscribe`, via e.g. "order-encode") to the sequence chosen in the app setting `order_encode_address_sequence` (sequence id; empty = no question; CEO only; a non-existent id is refused; set next to `order_encode_rules`, not in page settings, so S-130.7 stays true). Never for R5 duplicates, name, phone or price holds, a PROCEED row, or a not-accepted second order. At most one question per row (a later still-held reply goes to staff). `already` → no second subscribe; `refused` / no sequence → the row stays held for staff with the reason visible on /order-encode, flow not broken. Record the result as a chat event and on the order. | "magssend ng chat yung bot, mag-aask kung ano address"; triggered through a sequence the owner sets up. |
| **Fallbacks.** A failed first encode keeps today's sheet fallback (S-132.6/.10/.16). A failed re-encode of an existing row leaves the row unchanged, writes no sheet row, and marks the encode failed with a note. "Also write to Google Sheet" writes one sheet row per customer per day, not per trigger; `sheet_written` from an earlier trigger is respected. | No duplicate rows anywhere. |
| **Unchanged:** shadow pages (Bianca, Joy) and the Test tab behave exactly as now (no row, no link, no Astra, no sequence); replies switched off (S-132.11) → nothing queued. | Shadow comparison must stay clean. |

## Threat model and risk
Untrusted: customer chat text (encode input, GPT prompt, shown on /order-encode: escape it), GPT and Astra output, the sequence id in the setting (validate). Trusted: CEO settings actions, the J&T list. Risk tier: medium — it decides whether an order becomes a row and whether a customer is messaged, but no page uses the live path yet; switching a flow to it is a separate owner decision. Concurrency (double taps, queue workers, night run) is the main correctness risk: use a DB transaction / row lock or a unique key for "one open row per page + PSID".
