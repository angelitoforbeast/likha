# Brief 174: Page-based or Ad-based reply values, shown as an expanding row with each ad ID's status

## Why
Spec 172 put ad groups at the bottom of the page Edit window on /chatbot/pages, and a page is "ad-based" only implicitly (it has groups). The owner did not find it and wants it the way he described: each page has a visible setting, Page-based (default, as today) or Ad-based; an Ad-based page (e.g. Precious Lopez, many items running) expands in the pages table itself, showing its ad groups and their ad IDs, where the values used for the reply are set. He also needs to see each ad ID's state: new ads, On or Off, and how long an ad has been off, so groups are set up for the ads that matter.

## Decisions (do not reopen)
| # | Decision | Why |
|---|---|---|
| 1 | **Reply values switch per page:** "Page-based" (default for every page) or "Ad-based". Stored as one page_settings row (follow the 172 precedent; e.g. provider `adgroup`, key `mode`, value `ad`; absent = page-based), with history like other values. **Page-based ignores the page's groups entirely** (resolution returns the page values; groups are kept, not deleted). Ad-based applies 172's resolution unchanged. Same edit rights and throttles as page values (server-side). A page that already has groups when this ships stays page-based until someone switches it (today no page has groups). | Owner: visible option, page-based by default. |
| 2 | **Expanding row in the /chatbot/pages table.** The Reply values setting shows on each page row (compact select or pill + edit). An Ad-based page gets an expand control; expanded, sub-rows appear right under the page row: **Default** (the page's own values, as today) and **one sub-row per ad group**, using the same columns as the page row. In a group sub-row only the keys a group may set (172 decision 2) are editable, inline, saving like page cells (history, Restore); an empty cell shows the default's value muted with "uses default"; page-only columns show "page value". Below the groups: **Add ad group**. Page-based pages stay single rows exactly as today. Keep the Edit window's Ad groups section consistent (same data) or replace it with a pointer to the row — state which in the result. | Owner's picture: the page expands, ad IDs below, values set there. |
| 3 | **Ad IDs visible per group:** each group sub-row shows its ad IDs (expand "Show all" when many), each with the ad name from ads_manager_reports (campaign / ad set / headline, as 172's adNames), **status** (decision 5), customers in the last 30 days, and last customer time. Remove an ad ID from a group in place (history). | Owner: "makikita naman yun diba?" |
| 4 | **Adding ad IDs, two ways:** (a) manually: type/paste IDs (comma, space or newline; digits only, invalid ones refused with a message); (b) from the database: the "Ads not in a group yet" list for the page (172's unassigned: ads seen in this page's chats/customers in the last 30 days) with the same name/status/customers/last-time columns, sorted New first, then On, then by customers; tick several → add to an existing or new group. One ad ID in at most one group per page (172 rule). A count "N new ad IDs not in a group yet" shows on the expanded page (and as a small badge on the collapsed Ad-based row). | Owner: manual or via database. |
| 5 | **Ad status from data Likha already has — no Meta call per screen view.** From ads_manager_reports (filled by uploads and, once write mode is on, by the Meta sync): latest report day for the ad, its campaign_delivery / ad_set_delivery that day, and spend by day. Show: **On** (latest day's ad_set_delivery and campaign_delivery are both `active`, or spend > 0 on the latest report day); **Off since <date> (N days)** (otherwise; the date is the day after the last day with spend > 0, or the first non-active day if it never spent); **New** badge when the ad's first report day or first customer is within the last 3 days; **No report data** when the ad is not in ads_manager_reports (still show customers). Show "as of <latest report day>" once per page so the age of the data is clear. A group whose ads are all Off is shown muted with "all ads off". Read with one or two grouped queries per page expand (indexed by ad_id/day; check indexes exist — if a needed index is missing, stop and report instead of adding a migration), cached ≤ 5 min. | Owner: consider new ads, On/Off, how long off. |
| 6 | No change to how a reply is chosen for Ad-based pages (172), to sending, flows, sequences, chatblast, Forbeast, the Meta sync, or the Ads Manager report. No new tables. | Small and safe. |

## Cases (S-174)
P1: .1 every page shows "Page-based" by default; switching Precious to Ad-based writes one setting row with history; a non-editor cannot switch (403); .2 Page-based page with a group → a customer from a grouped ad gets the page values; switch to Ad-based → the group's values (172 behaviour); switch back → page values, groups still there; .3 expanding an Ad-based page shows Default + one sub-row per group with editable group cells; editing a group cell saves with history and Restore; an empty group cell shows the default value muted; page-only columns are not editable in group sub-rows; .4 a group's ad IDs list shows name, status, customers, last time; removing an ad ID writes history; .5 manual add parses "111, 222\n333", refuses non-digits, refuses an ID already in another group of the page (names the group); .6 "Ads not in a group yet" lists the page's ads with status, sorted New → On → customers; ticking two and adding to a group works; the "N new not in a group" count is right; .7 status: an ad with spend on the latest report day → On; last spend 5 days before the latest day → "Off since <date> (5 days)"; first report day yesterday → New; absent from reports → "No report data"; a group with all ads off → "all ads off"; .8 Page-based pages render as single rows unchanged; .9 existing 172/173 and Chatbot/Chatblast/Botcake/PageSettings suites pass. P2: .10 390 px (sub-rows stack readably).
