# Brief 175: the Forbeast watcher moves a page only when Forbeast is really at fault, and moves it back by itself

## Why
app/Services/Chatbot/ForbeastWatch.php moves a page from provider "gateway" (Forbeast) to "botcake" when Botcake has chats from ≥ 2 customers with no Forbeast copy after 120 s (condition "inbound"); records go to page_settings chatbot.auto_switch (JSON). Pages never move back by themselves. Investigation of the three waves (24 switches, Oct 26–27):
- Oct 26 22:05–22:21 Manila (12 pages): Forbeast's queue was backed up (messages 160–970 s late) — a real Forbeast fault (being fixed in Forbeast with a separate message lane and a new `inbound_lag_seconds` field on the per-page health response GET /api/v1/pages/{id}, which ForbeastWatch::health() already polls every minute).
- Oct 27 10:08: Forbeast delivered in 1–4 s but Likha stored the gateway rows ~2.5 min late — a Likha-side delay, not Forbeast.
- Oct 27 11:43–13:25: Forbeast was fast; some customers' messages never reached Forbeast at all (Meta did not send them, or they were lost before Forbeast recorded them). Other customers on the same pages in the same minutes were fine.
So one missing message, or Likha's own lag, moves a whole page, and it then stays on Botcake until someone moves it back by hand. Normal latency Forbeast → Likha is ~2 s.

## Decisions (do not reopen)
| # | Decision | Why |
|---|---|---|
| 1 | **Blame Forbeast only with evidence.** Before an "inbound" switch, require all of: (a) the missing-copy condition holds for **≥ 3 customers** and **≥ 300 s** (both in config with these defaults); (b) **Likha is not the slow one**: Likha's own queue that runs HandleGatewayEvent is not backed up (Horizon wait for that queue < 60 s, or the newest stored gateway row for any page is < 60 s old while gateway traffic is normal) — if Likha is behind, record an event "held: Likha ingest lag N s" and do not switch; (c) **Forbeast agrees or is silent**: if the latest health response has `inbound_lag_seconds` and it is < 60, Forbeast is healthy → do not switch the page; record "held: Forbeast healthy (lag N s), N customers missing — likely not delivered by Meta". If the field is absent (older Forbeast) or ≥ 60, the switch may proceed. Connection-code switches (CONNECTION_CODES: 190, 200, 2022, 613, 4, 32) stay immediate, unchanged. | Stop moving pages for Meta misses or Likha lag. |
| 2 | **Missing messages still get answered.** When a page is held (not switched) and a customer's Botcake chat has no Forbeast copy after the grace, answer that customer through the existing standby path (find how standby/Botcake copies are answered today — "standby skipped" logic in ForbeastWatch — and use it per customer). No customer is left without a reply. | The customer is served even when the page stays on Forbeast. |
| 3 | **Automatic switch back.** A page that the watcher itself moved (latest auto_switch record result "switched", from "gateway" to "botcake", condition inbound or send-related — not connection codes, and not a page a person set by hand afterwards) goes back to "gateway" when, for **30 minutes** in a row (config), Forbeast health is ok (connected, can_send, inbound_lag_seconds < 60 or absent and no missing copies), and there is no send failure. Record an auto_switch event "switched back" with the evidence. A person changing the provider by hand afterwards always wins (no switch back). At most one switch back per page per 6 hours (config). | Pages no longer stay stuck on Botcake. |
| 4 | **Visible reasons.** The auto_switch feed and the page's "Auto-switched …" note on /chatbot/pages show the held/switched/switched back events with the plain reason (e.g. "Forbeast slow: 412 s", "held: Likha slow 140 s", "held: Forbeast healthy, 2 messages not delivered by Meta", "back on Forbeast after 30 min healthy"). Keep the existing data shape; add fields, don't break readers (BotHealth, banners). | The owner can see why. |
| 5 | No change to sending, flows, chatblast, Forbeast, or connection-code handling. No new tables. The pages already moved on Oct 26–27 become eligible for switch back under decision 3 once this ships (they were moved by the watcher). | Safe. |

## Cases (S-175)
P1: .1 3 customers missing 300 s, Likha not behind, Forbeast health without the new field → switch (as today, stricter thresholds); .2 2 customers or 200 s → no switch; .3 Likha's ingest queue backed up 120 s → held, event recorded, no switch; .4 Forbeast health inbound_lag_seconds 3 → held "Forbeast healthy…", the missing customers are answered via standby; .5 inbound_lag_seconds 400 → switch with reason "Forbeast slow: 400 s"; .6 a watcher-switched page with 30 min healthy → switched back with an event; 29 min → not; a page set to Botcake by a person after the switch → never switched back; a second switch back within 6 h → not; .7 connection-code switch unchanged; .8 existing ForbeastWatch / BotHealth / chatbot suites pass.
