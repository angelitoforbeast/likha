# Brief 021: a filter on each column header of the RTS table

**The request, from the marketing lead through the owner:** on the page that shows "RTS Projection" and "Full Range" (two donut charts at the top; filters DATE RANGE, SEARCH, ITEM (EXACT) with the buttons Search Item, Apply and Reset; below them a table with thirteen columns whose headers read: DATE RANGE, SENDER, ITEM, COD, QTY, RTS QTY, the delivered quantity (its header is the three letters D-E-L followed by QTY), TRANSIT QTY, RTS%, DELIVERED%, IN TRANSIT%, CURRENT RTS%, MAX RTS%; a "Show N entries" control; a line like "Showing 1-15 of 15 entries (filtered from 313)"; and a TOTAL row), she wants a filter on the header row, "yung pwedeng mag-check kung alin ang ifi-filter": like the filter of a Google Sheet when its filter is switched on. Find the page by those words (grep the views for "RTS Projection", "PARTIAL COHORT", "MAX RTS"); say which route, controller and view it is.

**What to build:**
1. Each column header gets a small filter control next to its sort arrows. Clicking it opens a panel under the header with: a search box that narrows the list; "Select all" and "Clear"; one checkbox per distinct value of that column among the rows the page holds under the top filters (date range, search, item), sorted sensibly (text A to Z; numbers and percentages by value; date ranges by start date), each with its count of rows; and Apply and Cancel buttons. For the number and percentage columns add, above the list, a simple condition: an "at least" input and an "at most" input (either may be empty).
2. Several columns can be filtered at once (a row must pass all of them). A header with an active filter is clearly marked, and a "Clear column filters" control appears near the "Show N entries" line when any is active. The page's existing Reset button clears them too.
3. The column filters behave exactly as the existing SEARCH box behaves for everything downstream: read how the search box is wired today and feed the column filters into the same path, so that whatever follows the search today (the table's rows and paging, the "Showing ... (filtered from N)" line, the TOTAL row, and the two donut charts if they follow the search today) follows the column filters in the same way. Say in your final message which of those follow the search today and so follow the column filters. If the charts are drawn by the server from the top filters and do not follow the search box, leave them so and say so.
4. Changing a top filter (date range, item, Apply) reloads the rows: keep the column filters whose chosen values still exist, drop the others without an error. The panel is usable by keyboard (Tab, Space, Enter; Escape closes) and closes when clicking outside; only one panel is open at a time; on a narrow screen the panel stays inside the viewport.
5. No change to who may open the page, to the numbers, or to the server's queries unless the table is paged by the server (if it is, say so before building: then the distinct values and the filtering must be done by the server, across all pages, and the brief's "rows the page holds" means the whole filtered set; build it that way).

**Tests:** if the table is filled and filtered in the browser, put the filter logic (distinct values with counts, the checkbox set, the at-least and at-most condition, several columns together, the keep-or-drop rule after a reload) in a small script file with no page dependencies and test it with `node` the way the repo tests other scripts, or with the nearest convention the repo has; plus a server-side test that renders the page (as a user who may open it, with invented rows) and asserts the header controls and the script are there. If the server filters, feature tests for the query. The whole existing suite must still pass (the project has one known old failing test; name it if it shows). Show the new tests failing before the code where that is natural.

**Final message:** what the page is (route, controller, view), how it was built (browser side or server side) and why, the test lines, what follows the column filters, anything you could not check (no browser here: say exactly what a person should click to check it on the live site after release), and the commit ids. One clean commit for the feature is preferred (the reviewer squashes onto develop).
