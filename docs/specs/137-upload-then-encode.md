# Brief 137: an Upload to macro block writes the order row first; the Encode order block then encodes that row (with an optional Astra check) and gives the flow its result

## Why
Today one flow block, "Encode order" (specs 132 and 136), encodes the chat, writes the macro_output row (one row per customer per day), runs Astra on the spot and may subscribe the customer to an address sequence, all in the background while the flow moves on. The owner wants two blocks so he can put his own logic between the result and the next step: first save the order (Insert or Update, like a Google Sheet insert/update action), then encode it, wait for the result, and decide with a Condition (for example, an address hold → his own Sequence block that asks for the address). Saving first means no order is ever lost, so no Google Sheet backup is wanted. He also tests repeatedly on one page, which needs Insert.

Facts in the code (read them): `FlowEngine::encodeOrder()` queues `EncodeOrder` and continues at once; the 'ai' block suspends the run (`aiPending`, "waiting for the AI answer") with a deadline and `ChatbotAiQueue::sweep()` that resumes a late ticket on its failed port, and holds the customer's later chats while pending — reuse that mechanism for the wait (no new table unless it truly cannot work; then explain in Open points before adding one). `LiveOrder` (find/create/update), `Conversation`, `Duplicates` (R5), the customer lock and `RowLock` are in `app/Services/OrderEncode/`; `RunSpotAstra` / `AiCheckerRowRunner` / `AstraEncoder::processRow($id)` fix a saved row.
