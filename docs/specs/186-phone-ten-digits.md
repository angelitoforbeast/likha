# Brief 186: encoded orders store the phone as 9XXXXXXXXX (10 digits), and existing 09… rows are converted

## Why
Since 2026-10-28 Likha's own order encode (App\Services\OrderEncode\LiveOrder, around line 159: `'PHONE NUMBER' => OrderPhone::forOrder(...)`) writes `macro_output`.`PHONE NUMBER` as `09XXXXXXXXX` (11 digits; BotcakeCustomerMatcher::normPhone's form). The website's convention, from the sheet era (Google Sheets drops the leading 0), is `9XXXXXXXXX` (10 digits): Validate (App\Services\MacroChecker, "PHONE hindi 10-digit na 9XXXXXXXXX") hard-fails every 09… order, its same-day duplicate check (`duplicatePhoneRows`, exact `where('PHONE NUMBER', $phone)`) misses a customer with one 9… and one 09… order, and Astra (AstraAddressRules), the encode duplicate check (OrderEncode\Duplicates) and the phone whitelist use 10 digits. Data on live: Oct 24–27 about 1,500–2,000 rows/day with 10 digits and 1–8 with 09…; Oct 28: 823 with 10 digits vs 767 with 09…. J&T upload (Jnt\JntPayloadBuilder::normalizePhone) and the J&T checker (JntCheckerController::normPhone) normalize both forms to 09… themselves and must keep working unchanged.

## Decisions (do not reopen)
| # | Decision | Why |
|---|---|---|
| 1 | **Fix at the source.** Every place Likha writes `macro_output`.`PHONE NUMBER` from the encode (LiveOrder and any other writer you find: grep the writers of 'PHONE NUMBER') stores `9XXXXXXXXX`: a valid PH mobile in any form (09…, 9…, +639…, 639…) becomes its 10 digits starting with 9. An invalid or empty phone stays as today (empty), so Validate still flags it. Add one small helper for the website form (e.g. `OrderPhone::website()` / `tenDigits`) and use it; do not change `OrderPhone::forOrder` / `normPhone` themselves (other features match on the 09… form). The "edited_phone_number" / staff-edit protection logic in LiveOrder must behave the same (a 09… vs 9… difference of the same number is not an edit). | One format on the website; Validate, duplicates, whitelist, Astra already expect it. |
| 2 | **Convert existing rows** with an artisan command (e.g. `orders:phone-ten-digits`), `--dry-run` by default printing counts per day and 5 samples; `--apply` converts exactly the rows whose `PHONE NUMBER` matches `^09[0-9]{9}$` (all dates) to the 10 digits, in chunks, idempotent, and logs each change (id, before, after) to a file under storage/logs (no new table). Nothing else is touched (other lengths stay for humans to fix). It must not change `updated_at`-driven behaviour that would re-trigger encode/validate in a harmful way — check what reacts to macro_output updates (observers, HISTORICAL LOGS) and state it in the result. | Owner approved converting the existing ones. |
| 3 | **Defensive:** Validate's same-day duplicate phone check matches both forms of the same number (`[$p, '0'.$p]`), like OrderEncode\Duplicates already does. | Old/mixed rows still caught. |
| 4 | No change to J&T upload, J&T checker matching, Validate's rules otherwise, sending, flows. | Safe. |

## Cases (S-186)
P1: .1 an encode with customer phone "0917 123 4567" writes `PHONE NUMBER` = 9171234567; "+63 917-123-4567" → 9171234567; no phone → empty as today; .2 a row whose staff already set 9171234567 is not reported as edited when the encode finds 09171234567; .3 the command's dry run counts rows `^09\d{9}$` and changes nothing; `--apply` converts them, leaves "0917123456" (10 digits starting 0), 12/14-digit and empty rows untouched, and a second run converts 0; .4 Validate passes the phone of a converted row; two same-day orders 9171234567 and 09171234567 are flagged as duplicates; .5 J&T payload phone for 9171234567 is still 09171234567; the J&T checker still links a waybill whose receiver phone is 09171234567 to an order with 9171234567; .6 existing OrderEncode, MacroChecker/Validate and Jnt suites pass.
