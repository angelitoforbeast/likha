| Change | Why |

| **Log what the bot did.** Each flow run writes small event rows. Events: run started (with a reason: new / resumed after wait), condition result (which row or `no`), field changed (`CHAT STATUS was set to LOOP 1`, `ALL USER INPUT appended`, `cleared`, `all fields cleared`), AI call (success or failed, model, saved to which field, without the prompt text), sheet row (written / failed), waiting for reply at step nX, run ended (reason), and paused or skipped (bot paused, replies off, chat too old).<br>• Store them in a new table `chatbot_events`: page_id BIGINT, psid BIGINT, chat_id, flow_id, node_id, type, detail JSON (short; values are cut to 200 characters), created_at.<br>• Indexes: (page_id, psid, created_at) and (created_at).<br>• Keep 30 days; extend the existing prune schedule, or add a prune command. | The owner wants to see the actual executed actions. Kept separate from `chatbot_replies` so sends stay small to scan. |
| **The thread gets a "View executed actions" checkbox** at the bottom of the right panel, as in CBB. When it is ticked, the events appear in the middle column between the bubbles as small centered grey system lines with an icon, in time order. Examples: "Custom field value changed — CHAT STATUS was set to LOOP 1", "Condition n20 → row 1", "AI step n25 → success (saved to GPT INPUT)". The choice is remembered in localStorage. | As in CBB. |
| **The right panel adds collapsible sections, as in CBB:**<br>• **Executed flows/steps:** the last 20 runs, with time, flow, the path of nodes and the result.<br>• **Error logs:** failed sends and failed steps, with the reason.<br>• **Media and files:** the images the customer sent (from `payload.image_url`).<br>Tags and Notes are out of scope. | Same layout the owner uses daily. |

| **Volume.** Events are written in one insert per run (batched), never one per query. The thread loads events only when the checkbox is on, within the same time window as the bubbles. | 1M chats/day. |
