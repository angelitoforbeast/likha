# Brief 131: Pancake conversations are keyed by the customer's PSID (Sender ID), and "See more" shows the right person's chat

## Why
Staff export messages from Pancake (Analytics → Export messages) per page and upload the .xlsx files at "Import Pancake Conversations" (`ProcessPancakeConversationsUpload` → table `pancake_conversations`: `pancake_page_id`, `full_name`, `customers_chat`). Today a conversation is keyed by **page + name**, and readers match by **name only**: the "See more" link on the macro output page (`MacroOutputController::pancakeMore`, `has_pancake` in the list query) takes the newest row with `full_name = fb_name`. 688,426 rows have only 564,775 distinct names, so a same-name customer's chat can show, and orders without a Facebook name never get "See more".

The export has a **"Sender ID"** column, which is the customer's PSID on that page. Checked on a real export (page 578379192022484, headers exactly: `Message content`, `Sender name (customer_name)`, `Sender ID`, `Page ID (page_id)`; 5,247 rows, 2,087 Sender IDs, all 17 digits): 229 Sender IDs equal `macro_output.botcake_psid` of real orders and all 229 have the same name; 2 names in that one file have two different Sender IDs. The export macro will always include Sender ID; files without it must keep working.

## Decisions (do not reopen unless something is actually broken)
| Decision | Why |
|---|---|
| **One migration, additive:** nullable `psid` (string, 32) on `pancake_conversations` + index (`pancake_page_id`, `psid`). Nothing else changes in the schema; old rows keep `psid` null. | No new table when a column on the existing one does it. |
| **Import:** find the header containing "sender id" (case-insensitive, same `findHeaderIndexContains` style); read it **as text** — never through a float (17-digit IDs lose digits in a double); trim, keep digits only, accept 10–25 digits, else treat as missing. Aggregate per **page + psid** when the row has a psid, else per page + name as today. Write: if a row with the same page + psid exists → update its chat (same append/replace rule as today) and its `full_name` to the newest name; else if a row with the same page + name and **psid null** exists and that name maps to exactly one psid in this file → fill its psid and update it (this adopts old rows); else insert. Two different psids with the same name in one file → two rows. Keep every current filter (phone check etc.) and the upload log counts (inserted / updated / skipped); add a count "with PSID" to the log if there is a free place, else note it in the result. | PSID is the exact person; old name-only rows get adopted instead of duplicated. |
| **One lookup service** (e.g. `App\Services\PancakeChat::forOrder(page name, fb name, psid)`): (1) psid present → `pancake_conversations` where psid = it (and the page's Pancake page id when the existing page-id mapping resolves it; otherwise psid alone, PSIDs are page-scoped) → newest; (2) no psid match → page + name (via the mapping) → newest; (3) else name only → newest. Returns the chat plus how it matched: `psid`, `page_name`, `name_only`. | One rule for every reader. |
| **"See more":** `has_pancake` and `pancakeMore` use the service (send the order id or psid + page with the request instead of only fb_name; keep the request validated and CSRF as today). Show a small grey label after the loaded chat: "Matched by PSID" / "Matched by page and name" / "Matched by name only — may be another customer". The list query must stay one query (no N+1): compute `has_pancake` with an EXISTS on psid OR (name) as it does now. Orders with a psid but no name now get "See more" when a psid row exists. | Right person; staff can see how sure it is. |
| Also switch `PancakeRetrieve2Controller`'s page + name match to the service's order (psid first) only if it is a small, clearly safe change; otherwise leave it and list it in the result. **Do not change** `AstraEncoder` or `MacroChecker` (separate processes); list in the result where they read `pancake_conversations` by name and what the one-line switch would be. | Keep the change small. |

## Threat model and risk
Untrusted: uploaded files (malformed headers, huge cells, non-numeric Sender IDs), chat text shown on the page (escape it). Trusted: staff session. Risk tier: medium (writes `pancake_conversations`, which Astra and the checker read; their behaviour must not change for rows they already match).

## Done when
- Tests: an export with Sender ID inserts rows with psid; the same psid in a later file updates, not inserts; a name-only old row is adopted (psid filled) when its name maps to one psid; two psids with the same name → two rows; a file without Sender ID behaves exactly as today; a 17-digit Sender ID stored as a number cell in the xlsx fixture keeps all digits (or the test documents that the export stores it as text and the reader forces text); non-numeric Sender ID ignored; the service returns psid / page+name / name-only matches in that order; "See more" returns the PSID customer's chat and its label, and the escape of chat text; `has_pancake` true for a psid-only order; no N+1 on the list.
- `php vendor\phpunit\phpunit\phpunit tests/Feature/Chatblast tests/Feature/PageSettings tests/Feature/Botcake tests/Feature/NightRun` plus the new tests pass; note the known local-only failure (missing Google credentials file) separately. Existing Astra / MacroChecker tests unchanged and passing.
- Result: files, migration name, the import's key rules, the label texts, where Astra/MacroChecker/Retrieve2 read by name and what was done or left, commits.

## Out of scope
Changing Astra or MacroChecker; backfilling old rows by other means; the Pancake export macro itself; any deploy.
