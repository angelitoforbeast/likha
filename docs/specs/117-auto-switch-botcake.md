# Brief 117: a Forbeast page switches itself to Botcake when Forbeast fails

Each page replies through one provider (`ChatbotProvider`, page setting `chatbot.provider`: Botcake or gateway = Forbeast; spec 111/113). Inbound follows the same switch: `HandleGatewayEvent` ignores Forbeast events for Botcake pages, and `BotcakeChatController` skips Botcake chats for gateway pages (~line 129, counted `gateway_page`). The owner, 2026-10-23: Forbeast is the main provider and Botcake is the backup; when Forbeast fails, the page must move to Botcake by itself; moving back is manual (the owner does it); he is told on Messenger (Mira's side polls Likha and messages him — Likha only exposes the events).

## Decisions
| Decision | Why |
|---|---|
| **Failing conditions, per gateway page** (checked by a scheduled command every minute plus inline on send results where cheap): (1) 5 consecutive failed Forbeast sends for the page, not counting customer-side errors (Meta #551 person unavailable, #10/outside window, user blocked/deleted — keep the list in one constant); (2) any Meta connection error from a send: token/permission/rate (#190, #200, #2022, #613, #4, #32 — one constant) → immediately; (3) Forbeast does not answer (timeout, HTTP 0 or 5xx) 3 times in a row; (4) Botcake delivered ≥3 chats for the page in the last 5 minutes while Forbeast delivered 0 → inbound broken; (5) health check every minute `GET /v1/pages/{id}` with the page's Forbeast token (113) fails 3 times in a row, or answers `connected=false`/`can_send=false`. Thresholds in config with these defaults. | The owner's "failing" rules. |
| **Switch**: set the page's provider to Botcake through the same path the page-settings switch uses, recorded in the page's change history with who = "auto-switch" and the reason (condition + last error). Only when the page has Botcake set up (token present); otherwise do not switch, record an event "cannot switch: no Botcake" instead. Never switch back automatically. | Manual return. |
| **Standby chats**: for gateway pages, Botcake chats are kept (stored, flow NOT run) instead of dropped, so condition 4 can count them and so the switch can answer them. On switch, standby chats of the last 15 minutes that have no reply yet and whose mid was not already handled from Forbeast (dedupe on `message_id` = mid, as `HandleGatewayEvent` does) are run once, oldest first. Use an existing column/marker if one fits; else one nullable column (migration allowed, nullable/defaulted only; say so in the result). | No customer left unanswered during the outage. |
| **Events feed for Mira**: `GET /api/chatbot/provider-events?since=<id>` with its own read-only key (`CHATBOT_EVENTS_KEY` in .env, `hash_equals`, 401 otherwise); returns the switch / cannot-switch events: id, time (Asia/Manila ISO), page name, from, to, condition, short error text. No secrets, no customer text. Store events where the change history already lives (check precedent; no new table unless nothing fits — then say why). | Mira notifies the owner on Messenger. |
| **messaging_type**: sends to Forbeast use `RESPONSE` for replies to the customer's message and `UPDATE` for sequence steps (and anything not triggered by an incoming message). Forbeast's API already accepts `messaging_type` RESPONSE\|UPDATE. No message tags anywhere. | Meta policy. |
| Show on `/chatbot/pages`: the provider cell shows a small "auto-switched <time>" note with the reason on hover/details, until someone switches it manually. English text. | Visible to the owner. |

## Done when
- Tests: each of the 5 conditions switches a gateway page to Botcake once and records the reason; customer-side errors (#551) never count; a page without a Botcake token is not switched and gets a "cannot switch" event; nothing ever switches back by itself; standby Botcake chats are stored without running while on Forbeast, and after a switch the unanswered ones of the last 15 min run once (a mid already handled from Forbeast is not run again); the events feed needs the key and returns the events since an id; sequence sends go with UPDATE, replies with RESPONSE.
- `vendor/bin/phpunit tests/Feature/Chatblast tests/Feature/PageSettings tests/Feature/Botcake` passes (plus any test folder you touch).
- Result: files, migration (if any), config keys, the scheduled command, the feed contract, commits.
